# Notification and announcement email visuals

This is a pure rendering and fictional preview slice. No email binding, send call, recipient selection, subscription/consent change, automatic dispatch, retry job or credentials are added. The existing auth/invitation email templates and live production version remain intact.

`notificationEmail(input)` and `announcementEmail(input)` from `backend/src/family-update-email.mjs` return `{subject, preview, html, text, theme}`. Content is plain text: title, preheader, paragraphs and an action label. HTML is escaped; links must use the HTTPS `greenwhitefamily.com` origin without credentials. Titles/preheaders reject line breaks and control characters. There is no raw-HTML body slot. A future caller must supply already-authorized content; this renderer does not decide what private information may be emailed.

`familyEmailTheme(appearance)` reuses the actual app palette, heading choices and accent resolver. Supply `{theme: 'light'|'dark', headingFont: 'sans'|'serif', interfaceAccent: {mode: 'family'|'profile'|'custom', color}, profileColor}` only when an explicit recipient appearance is available. Default is family light with Momo Trust Display, Inter body and the established two-line wordmark/oak. DM Serif Text is the existing alternative. Missing/invalid inputs use defaults; a profile color alone never silently becomes the interface color. No localStorage, member lookup or persistent preference is introduced.

Email layout uses presentation tables, inline solid colours and `bgcolor` fallbacks, with a fluid560px content column. No glass, gradients, shadows or decorative card borders. Font-capable clients can load the same public Google font assets used by GW; fallback stacks are Arial/Helvetica for sans/body and Georgia/Times for serif, with explicit Outlook conditional fallbacks. Mail clients may strip CSS, fonts or images, or recolour content in dark mode: exact cross-client appearance is not claimed. The wordmark is live text, so branding and content remain readable with the oak blocked. Selected yellow keeps its fill and uses readable dark button ink because this flat email omits the app glow.

The explicit light/dark choice is rendered inline and declared in colour-scheme metadata. There is no automatic mutation of recipient settings or attempt to infer device-local appearance from the server. Preview selection does not claim these choices are currently stored in recipient records.

Run `node scripts/preview-family-emails.mjs` for72 fictional HTML/plain-text pairs (default/eight accents ×light/dark ×two fonts ×two kinds), plus16 font/image-blocked fallbacks. Open `docs/family-email-preview/index.html`; the controls choose appearance, width and fallback. The generator downloads fixed public font assets once into this isolated preview directory, reuses the existing oak artwork unchanged, and performs no external writes. Preview content is a fictional Oak family, never actual member data. Bundled font licence texts are in `assets/*-OFL.txt`; canonical font sources are the fixed Google Fonts URLs in `family-email-theme.mjs` and `google/fonts` OFL directories.

Validation: backend tests cover escaping, link/header rejection, plaintext/content parity, explicit appearance mapping and contrast; frontend tests tie the default wordmark and palettes to actual app source. `node tests/email-preview-browser.mjs` exercises the local fictional matrix and selector, font-loaded and font/image-blocked rendering, overflow/focus and zero outbound requests. This is Chromium preview proof, not native Safari, physical-device or mailbox-client delivery proof.

Before real delivery, separately decide channel consent/preferences, eligible recipients and privacy, server-visible appearance persistence, event timing, idempotency/retries/failures and mailbox/provider validation. Unsubscribe/settings semantics are not fabricated in a renderer with no active subscription model. These decisions remain pending; no actual email is sent by this work.
