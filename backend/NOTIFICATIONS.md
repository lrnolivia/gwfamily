# Durable in-app notifications (0012)

## Release boundary

Apply `0012_notifications.sql` after migrations 0010 and 0011, before deploying the new Worker. It adds tables, nullable columns, transition revisions, indexes and database triggers. Existing notifications, read/dismiss timestamps and Following preferences remain intact. It does not create historical events, subscriptions, push deliveries, emails, credentials, cron schedules or network resources. Device push is deployment-gated; its activation is described below.

Domain triggers create immutable logical events and set-based inbox fanout inside the transaction that changes the resource. They cover posts/memories, new tags, comments/replies, actual reaction inserts, explicit leader announcements, consented birthday posts, household requests/email-invitation records, fee/order transitions, membership changes, meaningful reunion changes, conversation invitations/reinvitations/messages and membership/name/role changes. Updates with no relevant state transition create no event. A reaction removed and later added is a new logical event. Tokens, email addresses, post/message bodies, fee amounts, birth dates and contact fields never enter event metadata.

No more than one notice exists for an event/recipient. Tags win over ordinary Following when enabled; disabled mention categories can fall back to an independently enabled Following/announcement reason. Replies go only to the post author and immediate parent-comment author. Ancestors/dependents cannot become recipients. Fanout has no 500-recipient cap and rechecks active verified account/resource permissions in SQL at commit.

## API contract

- `GET /api/notifications?limit=50&before=<sequence>` returns `accountId`, `notifications`, full authorized `unreadCount`, `messageUnreadCount`, `readAllCutoff`, `nextCursor` and `settings`. Limits are 1–100. Sequence keyset pagination is stable for equal timestamps.
- `GET /api/me/notifications` and `PUT /api/me/notifications` read/update settings. Fields: `scope`, `selectedIds` (legacy `selectedMemberIds` accepted), `globalOff`, `categories`, `revision`. The legacy settings `pushEnabled` field remains false; current device readiness and enrollment come from `/api/me/push`. Concurrent revision conflicts return 409, rolling back the entire change. Existing choices referencing a subsequently unavailable member remain preserved; new selections require real active directory members.
- `POST /api/notifications/:id/read` and `/dismiss` are owner-scoped and idempotent. Dismiss does not change a chat read cursor.
- `POST /api/notifications/read-all` requires `{cutoff}` and cannot read notices newer than that observed sequence. `message.created` is excluded from generic read and read-all; conversation `read_sequence` advances mark corresponding message notices read atomically. The global bell excludes message unread counts, which belong to Messages.
- `GET /api/notifications/:id/open` resolves current resource authorization independently of the latest 100-post feed. Missing/expired/revoked resources return `{available:false,message}`. Older authorized posts include post/comments/memory/reaction/poll hydration from one transactionally guarded snapshot. No auto-accept or other domain action occurs on opening.
- `PUT /api/conversations/:id/notifications` accepts `{muted:boolean}` for the accepted participant. Muting suppresses that participant's conversation notices; unmuting never adds historic recipients.
- Notification writes accept `expectedAccountId`, and open accepts it as a query parameter. A shared-cookie account change returns 409 before mutation. List/settings/open responses carry the authenticated account ID for late-response checks.

Categories: `following`, `mentions`, `replies`, `reactions`, `announcements`, `birthdays`, `households`, `fees`, `orders`, `membership`, `reunion`, `messages`. In-app categories default on. Existing Following remains unchanged, including legacy Off. Independent global Off is absolute and preserves the member's Following choice in `notification_settings.following_scope`. Generic scope/category/selected-member patches keep Off unchanged until explicit `globalOff:false`; the legacy combined scope command can still explicitly turn notices on. Effective Off is mirrored as `notification_preferences.scope='off'` for older Workers and UI. Current categories, Following, membership/resource access, expiration and conversation mute are rechecked for lists/count/open. Turning settings back on may reveal previously eligible existing history, but cannot create recipients who were not eligible at commit.

## Retry and rollback

New command receipts store operation and canonical payload hash. Reusing a request ID with changed content returns 409; legacy receipts with no hash remain readable. Unique receipts and database batches roll back duplicate concurrent attempts together with domain/event/inbox writes. Legacy post/comment/shirt write routes now delegate to the command path and honor either a body `requestId` or `Idempotency-Key`; old callers without one remain compatible but cannot obtain retry identity across independent HTTP submissions.

An older Worker can run against the additive schema. A compatibility trigger suppresses its old generic notification inserts for resources already managed by typed events, including preference-suppressed fanout. It does not alter historical rows. Rolling code back leaves the durable event triggers active and preserves all preferences/history; the older UI may not display new typed non-post notices or independent global Off controls. Mirrored legacy scope Off makes its existing `memberMatches` filter hide historical notices, although the older server still returns the owner's own legacy rows. Compatibility triggers synchronize explicit older-Worker scope changes back to independent Off/Following and increment the settings revision; current settings transactions mark their preference write so the compatibility trigger does not double-increment. All historical rows remain intact. Do not delete tables or reverse migration columns to roll back a Worker release.

Email invitation creation/sending is unchanged: this release records its database transitions but does not add an email delivery outbox or request-idempotent resend/token workflow. Existing conversation invitations have no automatic expiry policy; generation tracking distinguishes actual reinvitations. No physical push/device, production database or email-delivery verification is claimed.

## Isolated verification

`npm --prefix backend test`, `npm --prefix backend run check` and `npm --prefix backend run build` use local code and fictional in-memory SQLite fixtures. New event/route tests exercise the ten audited defects, replay and final-statement rollback, global Off/category precedence, 125-notice pagination, 550-recipient fanout, cross-account stale requests, settings CAS, private-group removal, conversation reinvitation/read/mute/revocation, legacy migration preservation and rollback fanout compatibility. These are not substitutes for production rollout verification or physical-device tests.

## Device push activation (0013)

The explicit activation release applies `0013_push.sql` once after 0012 and verifies its tables, indexes and triggers before setting `PUSH_SCHEMA_VERSION=1`. The existing staged VAPID key pair is retained. Delivery requires `PUSH_ENABLED=true`, valid key/subject/version bindings and `push_control.enabled=1`; a missing gate leaves delivery off. A minute cron drains the bounded outbox; the existing hourly cleanup/birthday schedule remains. Rollback disables the flag/control and retains additive tables, preferences and inbox history.

`GET /api/me/push` exposes only the authenticated session’s device IDs and public application key when ready. Registration requires explicit browser permission, an active verified member, the current account/session, same origin and a validated provider subscription. Existing global Off, session/account revocation, rate limits and delivery-time resource/category checks remain in force. Opt-in and activation never backfill older notices. Push contains generic text and an opaque notice ID; opening it resolves current authorization on the server.

After explicit enrollment, `POST /api/me/push/devices/:id/test` sends one generic device confirmation to that account/session’s active device. It shares the five-per-ten-minute setup limit. Its response confirms provider acceptance only; checking the actual device notification is a separate delivery verification. Preview never enrolls devices or sends tests. No family-wide test notifications are created.
